# 引擎接入与验证

## 源码与 ABI

起点 `qwentts.cpp@51512f129a7419567f4b8abfb06801451789b8f1`；GGML 固定为
`2eddaf94a8cdbbf1c30017d28313cd661a9da543`。本 fork 的头文件和动态库必须来自同一提交。
ABI 版本提升为 6，最低版本也是 6；旧调用者须重新编译，不提供隐式布局兼容。

`qt_init_params.n_threads` 为 CPU 实际计算线程数，也用于 GPU 的 CPU 回退；
0 使用上游物理核数启发值，负数拒绝。CPU 后端没有线程配置入口时初始化失败，
不能把请求值冒充实际设置值。

`qt_init_params.backend` 严格选择 **GGML 设备名**，从 `qt_backend_device_info` 取得。
例如本机 M1 Max 的设备名是 `MTL0`，实际后端注册表名是 `MTL`（Metal）；`CPU` 是 CPU 设备名。
不能把后端名当设备名。指定设备缺席或初始化失败会拒绝，不会自动改为 CPU。
NULL 自动选择，并保留上游 `GGML_BACKEND` 环境变量语义；空字符串拒绝。
节点 sidecar 使用清空环境的沙箱，应通过参数显式传递选择。

- `qt_backend_device_count` / `qt_backend_device_info`：不加载模型地枚举注册表。
- `qt_backend_probe(device, n_threads, out)`：复用实际后端初始化，再立即释放；不加载模型。
  成功只证明设备初始化，不能替代模型激活小样本。
- `qt_backend_info(context, out)`：报告已加载上下文的实际后端、设备、类型、内存与已设置线程数。
  激活与推理回执必须使用此接口，而非只报告请求偏好。

枚举和 probe 的字符串由 GGML 注册表持有，有效期为进程生命周期，调用者不释放。
上下文查询的字符串在上下文存活期间有效。设备内存单位为字节；上游不提供时为 0。
`QT_BACKEND_DEVICE_IGPU` 是集成 GPU，`ACCELERATOR` 不能被误判为 GPU。

克隆条件使用 `qt_extract_voice_ref` 返回的 `float[1024]` 和 `int32[16,T]`，合成时传回
`qt_tts_params.ref_spk_emb/ref_codes/ref_text`。CLI `.rvq` 是 11-bit 打包流，不能直接当 int32
数组。条件与 seed 都应由节点持有；引擎不处理材料加密、授权或资源登记。

## 三平台构建

需要 Python 3.11+、CMake 3.14+ 和原生 C/C++ 工具链。先创建真实 GGML checkout 并切到上述
固定提交，然后把目录传给入口。入口校验提交与 tracked 文件干净状态，不读敏感目录。
构建目录必须在源码树和 GGML 树外；默认并行数 2，可由任务协调者调整。

```sh
sh scripts/build/macos.sh --ggml-source /外置目录/ggml --build-dir /外置目录/vc1-macos --jobs 2
sh scripts/build/linux.sh --ggml-source /外置目录/ggml --build-dir /外置目录/vc1-linux --jobs 2
```

Windows 在 VS Developer PowerShell 中运行（需 Vulkan SDK、CUDA toolkit 和 `dumpbin`）：

```powershell
./scripts/build/windows.ps1 --ggml-source D:/engines/ggml --build-dir D:/engines/vc1-windows --jobs 2
```

macOS arm64 构建 Metal + CPU，使用 ARMv8.2 + dotprod + fp16 通用基线与内嵌 Metal shaders，
不绑定开发机 `native` 指令集。Windows x64 构建 Vulkan + CUDA + CPU 多变体，Linux x64
构建 Vulkan + CPU 多变体。Windows/Linux 使用上游动态后端加载；库、后端模块和 worker
发行时必须同目录，不能只拷贝 libqwen。Linux 面向主人桌面，托管节点不安装本机模型引擎。

任意平台可用 `--plan` 输出参数而不执行；跨平台的计划不算真机验证。
每次成功生成 `build-receipt.json`，包含源码/GGML 提交、dirty 状态、完整命令、动态库 sha256
和动态链接集合。入口只构建，不签名、不发布。Windows/Linux 在真机发行证据前保持 unsupported。

## 有界验证

```sh
python3 -m unittest discover -s tests -p 'test_build_plan.py'
ctest --test-dir /外置目录/vc1-macos --output-on-failure
cmake --build /外置目录/vc1-macos --target voice-benchmark --parallel 2
```

前两项无需模型。C99 测试锁住公开 ABI，后端专项涵盖参数拒绝、无模型枚举、严格不存在设备、
CPU 1/8 线程配置、自动选择和探测释放后的字符串。CPU-only 构建也必须跑同一套测试。

`voice-benchmark` 是显式真实模型专项，不加入默认 CTest。首次可从已授权的 24kHz 单声道
f32 PCM 现场提取条件，随后用保存的条件重复合成，所有路径在源码树外：

```sh
voice-benchmark base.gguf tokenizer.gguf reference.f32 extract reference.txt target.txt first.f32 MTL0 8
voice-benchmark base.gguf tokenizer.gguf first.f32.spk first.f32.codes-i32 reference.txt target.txt repeat.f32 MTL0 8
```

输出 f32 PCM 和一行 JSON（实际后端、线程数、采样数、音频时长、计算时长、RTF、首音频毫秒）。
`first_ms` 是首次真实音频回调；`first_codes_ms` 是上游自报的首组声码，两者不能混用。
末尾加 `buffered` 可对照调研的批量解码口径，此时无音频回调，`first_ms=-1`。
同 seed 42、同条件、同后端三次结果应逐字节相同；Metal 克隆目标 RTF ≤ 0.5、首帧 < 100ms。
再用同条件显式 CPU 1/8 线程做耗时反例。首帧/RTF 从开始合成计算，模型加载和现场提取另记
墙钟与内存，不能把两种口径混用。性能不达标须记录原值，不替换阈值或报告假通过。

## 许可与发行边界

代码保留原 MIT，Qwen 权重使用 Apache-2.0 全文与来源记录（见 `NOTICE` 和 `LICENSES/`）。
本仓不提交模型或测试录音。可信安装包必须绑定实际权重摘要、模型来源修订和库精确提交。
上游改进 PR 应仅包含 ABI/实现/专项测试，平台接入说明与发行规则留在本 fork。
